# 1020 OA-VAT 完整系统作为外部基线：接入方案(讨论稿，未改代码)

2026-10-20。用户决定：先做外部基线，选 OA-VAT(Sun et al., CVPR 2026, github.com/SHWplus/OA-VAT, MIT,本地 `external/OA-VAT` @ cea1f6b)。目标是 1019 叙事稿里的 **A 层(系统级)比较**:OA-VAT 用它自己的感知、身份和控制，在我们的协议、种子和指标上闭环。

## 1. OA-VAT 原系统是什么(只读调研，2026-10-20)

**每步流程**(`tracking/ortrack_core.py`),**只用 RGB**,不用深度、位姿、IMU 和相机内参:
1. YOLOE 开放词表检测器(`yoloe-11l-seg`,用类名作文本提示)。只在开局、在线增强和重捕获时运行，跟踪期间不是每帧都跑。
2. 开局：拿检测框与离线准备的参考特征(用户手框目标图像 → DINOv3 特征 + 翻转)比对，选出目标。
3. 跟踪：每帧运行 ORTrack(CVPR'25 抗遮挡 ViT 单目标跟踪器，DeiT-tiny)。置信度低于阈值连续 3 帧 → 判丢失。
4. 丢失：Kalman 外推;每隔若干帧在预测框周围的 ROI 里(连续 3 次失败后改为全图)用 YOLOE + DINOv3 原型重捕获;超过预测时限 → REDETECT(重置原型，全图重搜)。
5. 在线增强：每 20 帧用跟踪框更新原型(EMA)。
6. 控制(`control/drone_control.py`,PID,只有 2 个自由度):偏航角速度 = PID(框中心的横向像素误差);前进速度 = PID(目标面积 0.12·W·H − 框面积，带 ±20% 死区);高度和横向速度恒为 0。丢失期间发一次零速度后悬停。
7. 「遮挡感知规划」是扩散策略救援，默认关闭(`--dp_enable`),**权重未公开**,训练数据来自 Unreal A* 轨迹。

**权重与可得性(10-20 实测)**

| 权重 | 状态 |
|---|---|
| DINOv3 ViT-B/16 | 本地已有(之前身份适配已在用) |
| YOLOE `yoloe-11l-seg.pt` | GitHub release 可经代理下载(70 MB) |
| ORTrack `ORTrack_ep0300.pth.tar`(DeiT-tiny) | **Google Drive 经代理可访问**(gdown 已列出文件)。10-06 记录的阻碍已解除 |
| DeiT-tiny ImageNet 预训练 | fbaipublicfiles,可自动下载 |
| 扩散策略救援 | **未公开，无法使用**(原系统默认也关闭) |
| Pose2ID / IPG | 只用于行人目标，与车辆无关 |

**原仓库不能直接运行的地方**
- `main.py` 引用的 `DRONE/drone_controller.py` 不在仓库里;
- 多处硬编码 `/home/ws0/...` 路径;
- 后台线程按墙钟时间运行;
- 默认使用 vith16plus 权重(本地没有)。

因此需要自己写一层适配：用自定义的 `video.read()` 和 `vehicle.send_velocity()` 驱动它的核心循环，或者把核心循环改写成逐步调用。

## 2. 需要拍板的设计决定

**D1 感知：建议跑两个变体**

| 臂 | 检测 | 跟踪 / 身份 / 控制 | 作用 |
|---|---|---|---|
| **OA-VAT 原版** | YOLOE(只看 RGB,可部署) | ORTrack + DINOv3 原型 + Kalman + PID,全部原样 | 忠实复现。感知比我们弱(我们用真值伪框),**对它不利**,论文中注明 |
| **OA-VAT 同感知版** | YOLOE 换成协议的真值候选框(与 Ours 相同的特权) | 同上 | **公平的系统级对比**:检测特权对齐，其余都是 OA-VAT 自己的 |

**D2 目标初始化(OA-VAT 原本靠手框参考图，没有语言消歧)**
- **建议**:参考图 = 共享属性开局选中的候选(与所有臂相同的初始化信息，也与已有的身份适配一致)。
- 可选诊断：用真值目标作参考(它的初始化上限),不进主表。

**D3 控制映射与调参**
- 把它的机体系输出(前进速度、偏航角速度，Tello 遥控单位)换算成我们的世界系 (dx, dy, dz, dyaw):dz = 0,保持高度。
- 我们的相机俯仰 −50°、分辨率 512 px,与它的 Unreal 设定(俯仰 0°,160×120 / 320×240)不同，所以速度比例和目标面积比需要重新定。
- **建议**:给 OA-VAT 一个预注册的调参网格，在调参种子上选出最好的一组(不用 dev-B / test),预算与其他基线相同。网格为面积比 {0.06, 0.12, 0.20} × 速度增益 {0.5, 1, 2},共 9 组。
- 以帧计的参数按 10 Hz 换算(3 帧判丢失、20 帧增强、15 帧预测时限)。

**D4 运行方式(偏离原实现，须披露)**
- 后台线程(增强、重捕获)改为在固定帧间隔同步执行，保证可复现。
- 扩散策略救援关闭(没有权重;原系统默认也关闭)。
- 所有臂开局前 90 tick 的专家暖机相同。

**D5 记分(必须预注册)**
- OA-VAT 没有「承诺的跟踪器 ID」。按 tick 把它的跟踪框映射到车辆:**跟踪框中心落在哪辆车的真值框内，就算在跟哪辆**(落在多个框内取最近的;一个都不落 = 无承诺)。这个映射只在评分端使用。
- M1、承诺正确、TR90 都按这个映射计算。Ours 的承诺框本身就是真值框，用同一映射得到的结果与现行口径一致(实现时核对)。

**D6 工程**
- 新建一个只收 RGB、相机位姿和本体状态的 OA-VAT 策略服务(同感知版额外收协议的候选框)。
- 依赖装在隔离目录(沿用 `runs/pydeps_oavat` 的做法):ultralytics、timm、pykalman 等。
- 真值访问审计照常进行:原版只允许读评分端的真值;同感知版只允许读协议特权感知。

## 3. 验证步骤

1. **开环检查(在我们的 CARLA 图像上)**:用已录制的帧和真值初始框跑 ORTrack 与重捕获，统计跟踪框 IoU、丢失和重捕获率，确认移植后在我们的图像上能正常工作。不通过就先排查，不进闭环。
2. **冒烟**:2 个种子 × 2 个变体，检查动作映射、悬停和重捕获流程、审计和记分。
3. **调参**:在调参种子(建议 93700–93739,与 V1–V5 共用)上跑 D3 的 9 组，按预注册规则选一组，之后冻结。
4. **dev-B 闭环**:2 个变体 × r0 + r1,与 Ours-CV、永不切换、re-ID 同种子配对;按中途检查规则执行。
5. **test**:并入 V1–V5 第 4 步的 test,作为系统级对比臂。

全部代码改动先过 codex 只读审查。

## 5. 风险
- ORTrack 是单目标跟踪器，在俯视、小目标(约 27 px)、相似车辆密集的场景里可能频繁漂移。这是它的真实表现，但要用开环检查确认不是移植错误。
- 控制只有 2 个自由度且没有高度控制，在我们的俯仰视角下可能难以取景;调参网格的作用就是给它公平的机会。
- 原系统的开局依赖手框参考图，没有语言。D2 用共享开局替代，论文要写明。
