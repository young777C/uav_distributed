## 0. 一页总览

**一句话**:做一个"用语言指定、在无人机上闭环跟踪车辆"的生成式规划系统(VLM + DiT 动作头,ACoT 机制),围绕"丢失后重新捕获正确的那辆车"建立**评测体系、仿真数据闭环、基线与消融**;主要产出是一套可信的诊断与评测方法,以及一串经预注册检验的负结果。

**任务定义**:空中主动飞行 × 语言指定目标车 × 外观相似干扰车消歧 × 具身闭环。杀手场景是长丢失后的预测拦截与重捕获。

**三个核心问题(WHICH / WHERE / HOW)**
- WHICH:丢失再出现后,认哪一辆车(身份)。
- WHERE:目标在哪、无人机该飞向哪(预测拦截)。
- HOW:控制器如何把目标框稳在画面里(DiT 动作头)。

**主线演进(时间顺序)**
1. 08 月:证明语言有用(H0)→ 发现分辨率才是最深的墙。
2. 08–09 月:闭环证据把瓶颈从 WHERE 移到 WHICH;建 re-ID 阶梯。
3. 09 月:发现 re-ID 吃了真值拐杖;可部署版掉到 0.36;语言重锚被证伪;控制侧两次修取景被证伪。
4. 10 月上旬:仿真器白送身份的问题(Sticky-ID 零假设)、数据 FOV 错位、重生成数据、跟踪器贪心→匈牙利。
5. 10 月中旬:身份模块重训两轮 FAIL;DeepSORT/OC-SORT 原版复现;预注册的"第 0 步上限判定";指标改 M1;发现飞行是 TR90 的主瓶颈。
6. 10 月下旬:自动优化循环(LLM master + worker);压力场景重设计;OA-VAT 完整版;主指标定稿;基线与消融四层设计。

**目前最硬的发现**
- 在旧协议上,身份上限只有 +0.089(U1 0.754 vs 永不切换 0.665),预注册判定 stop——**场景没有空间,任何身份模块都测不出来**。
- 在压力场景上上限 D=+0.284,通过;但 Ours 仍不如内部 re-ID gallery(自飞 M1 −0.102 显著)。
- 强跟踪器(DeepSORT/OC-SORT)的绑定轨迹被删后弃权,实测约等于"永不切换"。

## 1. 阶段一:语言是否必要(H0),2026-08-11 → 08-17

**问题** 旧数据上语言不起作用:一个纯几何位置分类器的错跟率约 3–5%,比整个 VLM 还低,语言冗余。没有这个前提,整个任务立不住。

**方案** 逐层拆掉让模型"不用语言也能蒙对"的捷径,每次只改一个变量。

**做法与结果**

| 版本 | 拆掉的捷径 | 有语言 / 无语言 |
|---|---|---|
| v3 | 位置、深度 / 跟踪距离 | 56% / 71%(假象,56% 只是几何下限) |
| v4 | 居中偏移 | 72%≈随机 / 76% |
| v5 | 分辨率 336→512 | **58% / 72%,差 ~13pp** |

**结论** 最深的墙是图像分辨率:336px + 90° FOV + 远距时车只有 12px,身份在 tokenize 时被抹平;512px 后车约 27px,语言首次干净成立。教训:空中小目标要用高分辨率,不能照搬机器人 VLA 的 224/336。

**踩坑**
- 指标被污染:argmax 平局 × 目标恒为 idx0 会"做假",要先净化指标再下结论。
- 线性探针在跨集上不迁移,但端到端 VLM-grounded 头能迁移(依赖 Qwen 的车辆知识)。

## 2. 阶段二:瓶颈重构与 re-ID 阶梯,08-31 → 09-06

**问题** 闭环成功率 SR 长期为 0,不知道墙在哪。

**方案** 设计 4 臂 WHERE 阶梯(ear → cv_gated → road → road_oracle,含近乎完美的目标真值锚),看给了完美目标位置后 SR 是否改善。

**结果** 即使给完美位置,`reacquire_lock_wrong ≈ 0.74` 在所有臂都不变 → 瓶颈是 WHICH,不是 WHERE。便宜的 CV(匀速)先验已经把 WHERE 补上了。

**re-ID 阶梯**(19 局同种子配对,`continuous_metrics.py`):正确跟踪帧占比 0.309 → 0.622 → 0.650 → 0.626 → 0.715;最长错跟时长 11.98s → 3.53s。

**度量方法学转向** latch-SR(90s 内任一 ≥2s 错窗即永久失败)由最坏窗口主导,饱和、无分辨力(身份更好,SR 反而→0)。改用连续量:正确跟踪占比、最长错跟时长、重捕获率与延迟。

**控制侧两次"修取景"被证伪**
- BC-居中(flow-matching 微调 DiT 末层):居中机械上升,track_seconds 33.8→2.2。
- Stage-3 RL(SVG 可微 rollout):训练内 R_center 0.78→0.98,闭环复现同样的失效。
- 机理:居中在身份下游,激进居中把"认错的车"的误差放大成甩头。

**踩坑**
- RL 可微实现:`action_sample` 的 `@torch.no_grad` 会切断梯度,要写带梯度的采样器;可微 rollout 太慢(45 分钟 0 个 epoch),降步数 + 子采样 ~30× 提速;投影要先对齐 numpy(<0.001px)再训。
- 曾用挑出来的"硬全败子集"对比全集,造成"SR 退化"假警报 → 立铁律:永远同种子配对;小 n 或短 smoke 不下结论(3ep 显示有效,6ep 反转)。

## 3. 阶段三:真值拐杖暴露,09-06

**问题** 复查发现 re-ID 的 gallery 每帧由 GT 目标身份播种(`policy.py:230-231`),0.31→0.72 是半-oracle 身份下的数字。

**方案** 改可部署 gallery:承诺槽播种、语言冷启动、语言重锚,全程不读真值;加"语言重锚"三臂(单帧 / 时序 EMA / oracle)。

**结果**
- GT 拐杖价值约 0.35:0.715 → 可部署 0.363,最长错跟 3.6s → 13.4s。
- 语言重锚:单帧 0.225、时序 EMA 0.291,**都低于无重锚 0.363** → 假设"语言兜底重锚"证伪、关闭。
- oracle 重锚 0.741:给出干净上界,问题被精确定义为"缺可部署、抗漂移的身份信号"。

**意义** 论文叙事从"re-ID 阶梯胜利"改成"诊断 + 负结果链 + 上界定义"。这次自查是后续所有"先验证上限再投入"纪律的起点。

## 4. 阶段四:仿真陷阱与数据整改,10-02 → 10-11

### 4.1 Sticky-ID 零假设(10-02/03)
- **问题** 候选的 `idx` 是 CARLA actor 编号,出画期间持久,身份证据按 idx 累积,"遮挡后重捕获"被仿真器白送;OC-SORT / DeepSORT / DAM4SAM 不读 idx,对比不对称。
- **做法** 0 参数基线 Sticky-ID(首个 tick 语言选车后永不切换),离线反事实 + 闭环确认(n=19)。
- **结果** Sticky 与 PGIF 正确比例相当(0.579 vs 0.525~0.576),最长连续正确 +10.4s(p=0.012)。
- **结论** Sticky-ID 必须进表 1;重捕获评测需要让 ID 在出画/遮挡时断开(真实 MOT 关联 + 遮挡判定)。

### 4.2 数据 FOV 错位(10-03)
- **问题** 原始数据 90° 被磁盘清理删除,09-04 按 `output.fov: 70` 重生成成真 70°,之后的离线产物(TAHRelM、BC 居中、Qwen LoRA)仍按 90° 投影,候选框错位。
- **处理** 以实际训练为准统一 90°,改回默认配置;读数据前先核对 FOV 与投影是否一致。

### 4.3 事件中心数据评审(10-03,Claude + Codex 双 Agent)
- 全车标注使重入事件约 20×(目标 20 / 相似车 185 / 干扰车 209),但在 TAHRelM 上 target-only 与 all-vehicles 无差异(4.7k 参数已饱和)。
- 主杠杆是 null 头 + 世界系运动与 Δt;瓶颈是"弃权锁死"(判不在→不写记忆→Δt 增大→更判不在)。
- **世界坐标脆弱**:3% 逐帧深度误差下世界系模型从 0.901 崩到 0.410,输给图像系;深度误差是罪魁(帧差速度放大噪声)。
- **结论** 全车数据对身份模块无净收益,价值在于评测协议;主张世界系运动必须同时报噪声鲁棒性。

### 4.4 数据重生成(10-09 → 10-11)
- **问题** 数据里车辆长时间静止(目标全程 2.5 m/s)。
- **根因** `TM.set_desired_speed(veh, 9.0)` 单位是 km/h,不是 m/s;另有背景车聚集导致路口死锁。
- **方案** 保持 90°,最小重生成 64 集;场景车 10–12 m/s,专家无人机上限 15 m/s;加 `_unjam_step`(静止 12s 强制变道、20s 挪走前车)。全部改动 config 门控,缺省与旧行为逐位一致。
- **质检** QC v1 → v2(未截断、无 ≥40s 静止、运动 ≥35%)→ v3(加穿楼 ≤5%)。
- **结果** 64/64 通过 QC v3,运动帧均值 0.58,楼内 0.34%,训练可用 98.65%,生成 `manifest.json`。

**踩坑(多个根因都很隐蔽)**
- 第一轮全量只过 23/64:`scene_manager.cleanup()` 从不销毁背景车;同步模式下新进程 `get_actors()` 在首次 tick 前返回空,清场失效;同城镇不 reload 地图,上一集背景车成为静止障碍累积 → 同城不重载只有约 10% 通过,重载后 85%。**修在编排器层(每集前 reload + 核验 0 车),不改生成器**,以免破坏 @3 逐位一致。
- CARLA 服务器 SIGTERM 无效,要 `pkill -9` 并匹配端口;`pkill -f` 带自身命令串会误杀 shell。
- 运动学无人机无碰撞 → 穿楼(最严重一集 13% 帧在停车楼里,标签为错误监督);用 CARLA 建筑包围盒量化,并加训练时帧屏蔽 `frame_mask: train`。包围盒有负尺寸,要取 abs。
- 帧号对齐是 tick − 90(实测),不是 −91。
- 所有生成代码都过 codex 只读审查(R1 MAJOR → R3 NO MAJOR)。

**工具** 数据生成看板 `datagen_dashboard.py`(stdlib HTTP,127.0.0.1:8767,视频用 PyAV,SSH 端口转发查看),显示进度、QC、每集带标注的 MP4。

## 5. 阶段五:闭环结果与外部基线,10-06 → 10-16

### 5.1 实验设计与协议
- 1006 设计稿经 codex 四轮(R1–R3 MAJOR→MINOR,R4 通过)。主指标改读 **policy 内部承诺**(旧 scorer 是每帧输出再 5 帧滞回,并不代表无人机实际跟随的车)。
- 协议 `sim_proxy_v2@3` = @2 + `env_determinism`(sync_setup、reload_world)。

### 5.2 跟踪器贪心→匈牙利
- **发现** 闭环运行的 v2 跟踪器一直是贪心匹配(镜像里没有 scipy,`TrackletAssigner` 静默回退),但参数是在有 scipy 的主机上按匈牙利调的。
- **做法** 写 numpy 版求解器 `acot/runtime/lsa.py`,加开关 `perception.tracker.assign: hungarian`。
- **结果** 离线 IDF1 0.589→0.654;闭环承诺正确 +0.085(p=0.02)。所有 10-03/04 的旧数字都是贪心下得到的。

### 5.3 @3 协议闭环(dev-B 39 局)
Ours 0.525 vs DAM4SAM 0.720 / re-ID 0.636 / xattn 0.634 / OA-VAT 0.622 / DeepSORT 式 0.569 / OC-SORT 式 0.392。
- conf_tau 增益重复后缩为 +0.059 n.s.(第一轮含挑选偏差,同配置两次相差 0.08)。
- DINOv3 两阶段规则:stage1 过、stage2 不过 → 主模型保留 DINOv2。
- DAM4SAM-S 把耗时减半,准确率 −0.049,仍高于 Ours → 差距不是骨干大小造成的。
- **如实结论**:"我们的身份模块优于现有方法"不成立。

### 5.4 身份模块重训(P0-2,10-12 → 10-14)
- Stage A(新数据):+0.060 [−0.026,+0.149] p=0.20 → FAIL。
- Stage B(+@3 on-policy DAgger,117 集):+0.016 → FAIL,对 A −0.044。
- 承诺错误帧不降(0.403→0.383),增益来自"无承诺帧减少",并非判别力变强。
- 同一权重重复两次相差 0.08 → r=2 检不出 0.06 量级的效应。
- **结论** 瓶颈不在训练数据分布;离线 @3 准确率 +0.015 不转化为闭环。保留论文权重,不再自动加轮。
- 坑:`codex exec` 在后台要 `< /dev/null`;`pgrep -f` 会匹配到自己的等待循环;`merge.py` 要校验文件 mtime 防止合并残缺的 DAgger 文件。

### 5.5 DeepSORT / OC-SORT 原版复现(10-16)
- 动机:原先的"DeepSORT 式"只是 160px 运动门 + 外观 EMA,不是原算法;外部基线必须用已发表方法原版代码。
- 克隆开源仓库(GPL-3.0 / MIT)直接导入、不改原文件。
- **关键发现** 协议 0.6 s 一步,同车相邻 tick 位移约 0.7 个框宽,IoU>0.3 只有约 30% → 原版在该协议下失效。用户定:两种都跑,10 Hz(每帧一步,决策仍 0.6 s)进主表。
- dev-B 预注册网格 12 组完成,但**每局绑定轨迹都被删除后永久弃权,93–100% 的局"开局后承诺不变"** → 12 组实际等同"粘住开局 ID"。按预注册选出的最优组 0.765 是赢家诅咒,不可信。
- 含义:所有身份模块(Ours、re-ID)都没超过"永不切换"。
- codex 抓到 OC-SORT 新建轨迹读回顺序错误(R1 MAJOR),修后 R2 通过。

## 6. 阶段六:预注册的"上限判定"与指标讨论,10-16 → 10-19

**问题** 用户要求"移除 DAM4SAM,迭代模型超过 re-ID"。动手前应先问:身份头在现协议下到底还有多少可提升的空间?

**方案** 设计第 0 步:比较 **U1(真值身份头)** 与 **永不切换**,预注册阈值(≥0.15 继续,<0.10 停)。

**结果**
- D = +0.089 [+0.009,+0.177],p=0.049 → 预注册判定 stop。
- 分解:出画截断 74–76/80 局,最后 18 s 全部出画;遮挡帧占画面内帧 35–38%,任何身份头都无法投票;身份只能影响可见帧。
- 换主指标 M1(严格跟随率:目标有框的 tick 中承诺 key 的框就是目标):D_M1 = +0.137,p=0.001 → 主指标改 M1,回到 V1–V5。
- **专家飞行对照(P1)**:TR90 从模型飞 0.23 → 专家飞 0.90,D_expert(M1) +0.272。**飞行是 TR90 主瓶颈,并掩盖了身份上限。**(这也修正了阶段二"控制不是杠杆"的结论:那只适用旧协议。)

**指标口径的坑** `scoring.py` 中承诺的跟踪器 ID 无框时沿用最后匹配的车,停在旧 ID 上也算"正确";指标不要求重捕获新 ID,只惩罚切到干扰车。

**架构复核(10-12,Claude + codex)** 确认图 v3 与代码不符:承诺门限 0.5(实为 0.05)、EAR 无 Stage-1 预热、DiT 训练用真值航点(从没见过 EAR 输出)、约 60% tick 由 EAR 航点驱动 DiT;WHERE 的位置是真值,须在论文中写明。出图 v4,codex 复核 MATCH。

**运行事故** 调度器 `Dispatcher.work` 不捕获 `run_unit` 异常 → 死锁。经 codex R1–R6 修复:验证客户端退出、隔离 quarantine、BookkeepingError 停止派发、reconcile、实验锁、孤儿客户端清理。已知未修风险(用户决定):调度器崩溃后孤儿策略容器迟到写审计。

**重捕获统计(10-18)** 跟对后不可见再回来,≤6 s 的真实再捕获:re-ID 0.82、永不切换 0.65、Ours 0.60;≥6 s 长缺口几乎都找不回(0.1–0.25)。65–80% 的"丢失"是共享跟踪器把承诺 ID 换给别的车,并非身份模块改承诺 → "TAH 记忆被写坏是根因"未证实。

## 7. 阶段七:自动优化循环(LLM 驱动),10-19 → 10-21

**问题** 手工迭代一次闭环要数小时,难以系统搜索设计空间;希望用 LLM agent 自动提方案、跑评测、晋升。

**方案** 移植 `ndas-v11` 的 av_perf_agent v11:LLM **master**(skill av-opt-master)经 assign.py 发任务卡,最多 4 个 **worker** optimizer(Claude Opus 5.5)经 submit.py 做 probe/promote;晋升在锁内串行;Temporal 工作流 + Postgres + dashboard(8888)。

**设计要点**
- 目标:按局配对的同 tick 重捕获率;护栏:承诺正确率不降。
- **G3 门控(≤20 min)**:专家飞行录制一次,之后**离线精确回放**(实测 600/600 逐 tick 一致,每局约 27 s);上线前四项自检(零校准、排序一致、匈牙利复现、确定性)。
- **知识库与 ndas 完全隔离**:KB 根目录、Postgres、Temporal 队列/namespace、compose 项目名、产物目录全独立;启动时若命中 ndas 默认值则拒绝启动。
- 场景由人工阶段先重设计并冻结,agent 不能改。

**踩坑**
- kill -9 重启 worker 后在跑的 activity 超时,run 进入 PAUSED_RECOVERY → 需 `POST /api/runs/<id>/resume`;改 workflow 代码会让在跑的 run 失去确定性,只能改 activity。
- 宿主机 10-20 重启 3 次 → compose 与 cyh-carla 设 restart unless-stopped + crontab `@reboot` 自启;watchdog 自动对账死进程再 resume,修复记录在 `fixes.md`。
- 宿主负载高(他人编译)时 CARLA 卡住;live parity 缺失的种子按 infra 问题换种子重试一次。
- "暂停"≠"cancel":Temporal cancel 不可逆,曾误发 cancel 被用户纠正。

## 8. 阶段八:压力场景重设计,10-20 → 10-24

**问题** 旧场景语言冗余、身份提升空间只有 0.112,创新评审全判 reject;第 0 步已证明旧场景没有空间。

## 9. 阶段九:指标定稿、因果分层与同种子一致性,10-23 → 10-24

### 9.1 主指标
- 预注册:TR(=TR90)、ID-F(仿 VOT-LT 的 Pr/Re/F,Re≡M1)、RA@6s(6 秒内重新捕获)、FRA@6s、RMTR。
- **独立性审核**(codex 与 Claude 各自计算,结论一致):F 与 Re 的 ρ≈0.95,RMTR/AUC 与 RA@6s ρ≈0.95–0.99 → 冗余。
- 定稿(路径 B):**TR、M1、RA@6s、FRA@6s**,Pr 为第一诊断,F/承诺正确/M2 入附录。理由:与预注册与 autotune 目标保持连续,M1 单独看不偏向保守方法。
- 发现:自飞下 U1 错锁 22 个中 21 个是**跟踪器 key 转手**(key 抖动 0.105 vs 回放 0.010;距目标中位 75 m vs 39 m),且 K=5 迟滞让真值头也换不过去 → U1 不是 FRA 的下界。

### 9.2 分层复核(专家回放 114 局)
- M1 分层 Holm 校正(14 层)后 Ours − re-ID 全不显著;FRA 上 Ours 每一层都更高(+0.17~+0.35)。
- Ours 错锁 94 次中 67 次发生在**目标已重新入画之后**,其中 56 次是 **PGIF 触发 force_conf 强制承诺,绕过 K=5**。
- 事件分类:重新入画时克隆车在场的事件占 33%(RA U1 0.97 / re-ID 0.21 / Ours 0.25)。→ 指明 W 线要先试 `ours_no_force_conf`。

### 9.3 出画归因
自飞目标出画 ≥1.2s 时,承诺落在目标/干扰车上的次数 U1 31/24、re-ID 32/36、Ours-CV 25/48 → "飞行没跟住"与"身份把无人机带走"各约一半(连 U1 也有 44% 是跟踪器转手)。**现有 autotune 的 G3 用专家飞行回放,测不出 WHERE 改动**(需 G3-SF 自飞录制)。

### 9.4 同种子场景一致性
- 场景构成(城镇、目标、干扰车型号颜色、速度、丢失窗口)40/40 一致;但 dev-S 自飞 **tick 0(专家暖场后)世界状态 14/39 种子在不同方法间不同**(位移 0.1–140px);只用 25 个干净种子重算后 Ours − re-ID 仍 −0.15 显著,但"永不切换 − re-ID"从 −0.10 变成 −0.01(不显著)。
- 线索:偏离是离散的少数几种状态;局首 actor 编号 <400(服务器刚启动)偏离率 6/15,≥700 时 16/156(Fisher p=0.006)→ 怀疑与 CARLA 服务器历史状态有关。**根因未明**,写"逐位相同"之前须查清。专家回放表不受影响(每种子只录一次)。

### 9.5 归类修正
用户定性:re-ID(ext_reid)是我们设计过程的产物(crop-DINOv2 ViT-S/14 + 多样性 gallery K=2,不训练),是"TAH 免训练消融",不是外部基线;外部最强只剩 OA-VAT。

### 9.6 基线与消融四层设计稿(10-24)
A 系统 / B 模块 / C 组件 / D 诊断。注意:现有 `ours_no_*` 配置都继承 `ours_final`(conf_tau 0.5、EAR),必须以 `ours_cv_tahS` 为父新建才能配对;`ours_no_gate_commit`、`ours_no_temper` 在任何协议下都没跑过。待决 6 项(DAM4SAM 恢复、Ours=tahS、论文框架、T2、OA-VAT 闭环、E3)。

## 13. 与岗位 JD 的对照(面试用)

| JD | 对应实践 | 可举证的要点 |
|---|---|---|
| 针对生成式规划算法的自动化评测体系 | 配置驱动的 `acot` 评测框架 + 调度器 + 配对统计 + 预注册判定 | 第 0 步上限判定;同种子配对;连续指标;指标独立性审核;分层与出画归因 |
| 场景重建 / 数据 | CARLA 场景生成、压力场景、QC v1–v3、建筑穿楼量化、同种子一致性检验 | 根因调查(km/h 单位、清场失效、FOV 错位) |
| 数据闭环 | DAgger(on-policy 采集 → 重训 → 闭环判定)、压力 DAgger | 两轮 FAIL 并如实报告;离线准确率不转化为闭环 |
| 大模型数据挖掘 / 自动标注 | 事件中心全车标注评审、语言指令生成、LLM master/worker 自动优化循环 | **弱项**:标注主要靠仿真 GT 派生,没有对真实数据做 VLM 自动标注 |
| 持续提升模型性能 | 自动优化循环 + 预注册门槛 | 结果多为负;亮点是知道**何时该停**与**为什么测不出** |

**被追问弱项时的说法** 标注规则源自仿真 GT;迁移到真实数据的路径是 VLM 打标 + 一致性校验 + 人工抽检,并沿用本项目的"先验证标注是否真有增益"的做法(全车标注 20× 事件但消融无净收益的结论即例证)。
