# 1007 · 在线闭环性能总表(baseline 与消融;截至 2026-10-07 01:00)

> **先说明口径**
> - `@1 / @2 / @3` 是**闭环评测协议 `sim_proxy_v2` 的版本号**,不是特征主干:
>   - @1:贪心跟踪器(1001 §5.5b / §5.5c 的口径);
>   - @2:匈牙利跟踪器 + 统一开局交接 + 逐步策略随机数(1006 设计 v4);
>   - @3:@2 + CARLA 环境确定性(先切同步再生成场景、每个种子前重载世界;1006_t0_log D10)。
> - DINOv2 / DINOv3 是**方法**的身份特征主干(`identity.tah.feature`),在任一协议下都可以跑。
> - **当前协议下还没有外部 baseline 的结果**:基线调参网格 `t0_grid_devB`(63 组 × 40 集,@3)排在 @3 pilot 之后，约 04:00 启动，预计 10-08 中午前后完成。下面第 3 部分的外部 baseline 数字来自已被取代的旧协议，只作历史参考。
> - 所有在线闭环：CARLA Town05,无人机语言指定目标跟踪；身份决策不读真值;候选框为仿真检测替身(真值投影 + 遮挡过滤)。

**指标**(1006 设计 §4;主指标为 policy 内部承诺)
- 承诺正确:策略承诺身份 = 真目标的帧占比(主指标)。
- TR90:承诺正确的帧数 / 固定时域 900 帧(90 s);集因目标丢失提前结束后的帧计为未跟踪。
- AUC-SR:τ ∈ [0.5, 20] s 的 SR(τ) 平均;一集成功 = 承诺锁错从未持续 ≥ τ,且未因目标丢失被截断。
- 最长连续正确 / 最长锁错(s):按策略承诺计。
- 开局锁对:第 12 步(第 3 个 S2 tick)身份输出是否为真目标。

**读法**
1. **属性开局是最大的单项贡献**:去掉后承诺正确 −0.25,开局锁对从 0.94 降到 0.33。
2. **PGIF 在部署设定下显著**(−0.13),但**在共享开局下没有可见作用**(+0.03,n.s.)。这说明部署设定中 PGIF 的增益很可能主要发生在开局阶段:去掉 PGIF 后开局锁对从 0.94 降到 0.75,而共享开局把这部分差异拿掉了。这一点直接影响论文中对 PGIF「开局之后维持身份」的机制表述，需要在正式的表 2(@3,冻结重复次数)中确认。
3. **现有权重无法用记录配方复现**:重训 s0 低 0.13,原因线索见 1006_t0_log「G13 结果与影响」。按预定规则，论文的 Ours 继续用现有权重。(10-12 / 10-14 补充：修正配方后，重训在 @3 下不再变差，但新数据 +0.060、新数据 + @3 DAgger +0.016,都不显著、都未过门槛;见 §4b「P0-2」。)
4. **主干**:
   - 同配方、同数据下,DINOv3 比 DINOv2 好 +0.079 [+0.010, +0.150](r = 2;第一阶段通过);
   - 但两个仅离线重训的版本都明显低于现有权重；零样本把现有权重的特征换成 DINOv3,与 Ours 无显著差别(−0.03)。
   - 第二阶段(DINOv3 完整配方对现有权重)在链 C 中，约 07:00 出结果。
5. **TR90 和 AUC-SR 的绝对值都很低**(TR90 约 0.16,AUC-SR 约 0.03)。原因是 Ours 有 91% 的集因目标丢失超过 18 s 被提前截断(平均 513 / 900 步):截断后的帧在 TR90 里计为未跟踪,AUC-SR 中被截断的集一律不算成功。两者只适合做组间比较。

- 只跑一次的组(重训 s0、零样本)运行间噪声较大：同一种子上承诺正确的运行间 SD 约 0.2。

## 5. 实时性、延迟与算力：评价指标与实验方法(设计稿,2026-10-07;未实施，待 codex 复审)

### 5.1 为什么现有评测测不到延迟

- **当前闭环是同步仿真**:CARLA 每一步都等策略算完才前进，所以计算再慢也不影响跟踪结果。表 1–5 实际上都假设「零延迟」。真实无人机上，S2 决策若慢于决策周期，用的就是过期画面，目标已经移动。
- 后果：身份模块越重(SAM2-L、DINOv3),在零延迟评测里越占便宜——它们付出的算力不会体现为性能损失。
- 系统的计算构成(按代码):

| 频率 | 计算 | 现有计时 |
|---|---|---|
| 每帧(0.1 s) | DiT 动作采样(32 层) | 无 |
| 每个 S2 tick(0.6 s) | Qwen3-VL-4B 编码 → 感知(候选 + crop-DINOv2 特征 + 匈牙利跟踪器)→ EAR / IAR → 身份模块(+ PGIF)→ WHERE | `t_s2_ms` 只覆盖 EAR / IAR / 身份 / WHERE;`t_identity_ms` 只覆盖身份模块。**VLM 编码与感知没有计时** |
| 开局 tick(第 0 / 6 / 12 步) | 另加属性开局(3× 高清帧裁剪分类) | 计入当 tick 的 `t_s2_ms` |
| 每集 | — | `cost.json`:GPU 显存峰值 |

- 公平性要点:Ours、re-ID、关联类基线复用感知阶段已算好的 crop-DINOv2 特征(跟踪器本来就要算),不计入身份耗时;OA-VAT 的 DINOv3、DAM4SAM 的 SAM2 是方法专属计算，计入。成本表必须分「共享栈」与「方法专属」两栏报告。

要回答的三个问题:
1. **成本**:每个方法的延迟、显存、参数量、计算量是多少？
2. **实时性**:能否在决策周期(0.6 s)和帧周期(0.1 s)内完成？
3. **延迟鲁棒性**:按真实延迟运行时，跟踪性能还剩多少？方法排序是否改变？

### 5.2 指标

**A. 计算成本**(参考硬件:NVIDIA A40 48 GB,独占)

| 指标 | 定义 | 报告方式 |

| 决策延迟 L_dec | 一个 S2 tick 从收到图像到输出新的 z_ex 与承诺 = VLM 编码 + 感知 + EAR / IAR + 身份 + WHERE | 常规 tick 与开局 tick 分开报 p50 / p95 |
| 分模块延迟 | VLM 编码、crop 特征、跟踪器、属性开局、身份、WHERE、DiT 各自耗时 | 堆叠条形图(共享栈 vs 方法专属) |
| 动作延迟 L_act | 每帧 DiT 采样耗时 | p50 / p95 |

### 5.3 实验方法

**E1 计算成本基准(离线回放，与闭环解耦)**
- 输入：用现有 `record_act` 录下的 act 消息。从 dev-B 选 10 集，覆盖开局、遮挡、多个相似车;所有方法回放同一组输入，计时与闭环轨迹无关，可比。
- 环境:A40 独占(不与 CARLA 或其他实验共卡);batch 1;与部署相同的数值精度;每个方法前 20 个 tick 预热不计;CUDA 同步计时(沿用 `_sync()`);每个方法重复 3 遍取中位数。
- 分模块计时：在 `Runtime.step` 与 `AcotPolicy.act` 中补 VLM 编码、crop 特征、跟踪器、属性开局、身份、WHERE、DiT 的计时器。DAM4SAM 是独立服务：服务端纯计算时间与 RPC 往返分开记录。
- 参数量与计算量用统计脚本给出。
- 产出：成本表(方法 × {专属参数、L_id p50 / p95、L_dec p50 / p95(常规 / 开局)、L_act、DMR、RTM、f_max、M_peak、ΔM、GFLOPs})+ 分模块堆叠图。
- 闭环批量运行中记录的耗时(现有 `ticks.jsonl`)受同机多进程干扰，只作参考，不进论文表。

**E2 延迟注入闭环(延迟鲁棒性)**
- 机制(新协议开关 `sim.latency`,协议新版本，如 `sim_proxy_v2_lat@1` extends @3):
  - 仿真仍为同步，保持确定性与同种子配对;
  - S2 tick t 算出的结果(z_ex、承诺、vlm_ctx)延后 d = ⌈Δ / 0.1 s⌉ 帧才生效;其间 DiT 继续用上一份 S2 结果出动作;
  - 若 Δ 超过决策周期，下一个 S2 tick 顺延到上一个决策完成之后(相当于降频)。
  - 延迟只由 Δ 决定，不受机器负载影响，可复现。
- 两种模式:
  1. **固定延迟扫描**:Δ ∈ {0, 0.3, 0.6, 1.2} s,所有方法相同 → 延迟曲线、Δ₉₀、AUC-Δ;
  2. **实时匹配**:每个方法用 E1 测得的自身 p95 L_dec → pc_correct@RT。
- 补充维度：决策周期 T_dec ∈ {0.6, 1.2} s(算力减半)。PGIF 与承诺的参数目前以 tick 计(如 absent_max = 8 tick = 4.8 s);周期变化时需预先规定按秒保持语义(建议)还是按 tick 保持。
- 臂:Ours、w/o PGIF、re-ID、DeepSORT 式、DAM4SAM、OA-VAT(覆盖最轻、最重和最强的基线)。
- 种子与重复：先在 dev-B 跑 pilot(n = 40,1 次)验证实现;正式在 test(n = 80)单次运行。作为**探索性**结果，只报效应量与 CI,不进 Holm 族，不改表 1–5 的预注册。
- 预算:6 臂 × 3 个非零 Δ × 80 = 1,440 集(Δ = 0 复用表 1)+ 实时匹配 6 × 80 = 480 集，约 1,900 集;按约 90 集 / 小时约 21 小时。可缩减为 4 臂、Δ ∈ {0.6, 1.2} s(约 1,000 集)。

**E3 边缘设备(可选)**
- 如能拿到 Jetson AGX Orin,用同一回放基准测 L_id 与 L_dec;拿不到就只报 A40 数字，不做换算外推。

### 5.4 统计与报告
- 计时为描述性：报中位数与 p95;p95 的 CI 按集分块、对 tick 做 bootstrap。不做显著性检验。
- 延迟曲线：每个 Δ 报主指标均值与种子 bootstrap 95% CI;同一 Δ 下方法间配对比较(探索性)。
- 新增论文表：「表 6 · 计算成本」(E1,正文或附录)与「表 7 · 延迟鲁棒性」(E2,探索性)+ Pareto 图。

### 5.6 可能的结论与风险
- 可能的 claim:
  1. 我们的身份模块专属开销 < 3 ms、4,740 个参数，比 OA-VAT(约 45 ms)、DAM4SAM(SAM2-L)低一到两个数量级;
  2. 在实时匹配评测下，重型基线因延迟进一步变差，排序优势扩大(待 E2 验证)。
- 风险：共享 VLM 前端若很慢，「系统实时」无法声称，只能声称「身份模块几乎不增加成本」;延迟注入后所有方法都大幅下降、差距被压缩，也是可能结果，需如实报告。

- 公开规格:A40 FP16 稠密约 150 TFLOPS、696 GB/s;AGX Orin 64 GB 为 275 TOPS INT8(稀疏)、204.8 GB/s、15–60 W;Orin NX 16 GB 为 100 TOPS、102.4 GB/s、10–25 W;AGX Thor 为 2070 TFLOPS FP4(稀疏)、128 GB、273 GB/s、40–130 W。
- 小批量推理常受内核启动与 Arm CPU 侧开销限制，实际倍数需在端侧实测(E3)。

**判断**
1. **按现在的实现，任何方法都不能在端侧实时运行，瓶颈是共享栈而不是身份模块**:DiT 每帧 282 ms,在 A40 上就已是 10 Hz 帧预算的约 3 倍;整条 S2 链路在 Orin 上超出 600 ms 预算 2–7 倍。论文目前不能声称系统实时。
2. **共享栈有明确的工程优化空间**(对所有方法相同，属于工程问题):
   - 动作分块执行:DiT 每次生成 16 步动作，现实现每帧重算、只执行第 1 步;改为每个 S2 tick 生成一次、执行多步，DiT 调用次数可降 6–16 倍(会改变闭环行为，需重新评测);
   - 减少流匹配步数(8 → 2–4,或蒸馏)、bf16 / TensorRT / CUDA Graph 消除逐层 Python 开销;
   - VLM 用 INT8 / FP8(Thor)或 INT4(Orin)量化;S2 周期可放宽到 1.2 s(配合 §5.3 E2 的延迟评测)。
   - 估计优化后:Thor 上整体可达实时;AGX Orin 勉强(VLM 需 INT4/INT8);Orin NX 很难(需更小的 VLM 或更长的决策周期)。
3. **身份模块的端侧友好度差别很大**:Ours、re-ID、关联类、xattn 的专属开销在端侧也可忽略(< 20 ms);OA-VAT 中等(Orin 上 +0.1–0.3 s);**DAM4SAM 最重**(SAM2.1-L 每 tick 约 0.27 s,Orin 上推算 +0.8–1.9 s),在 Orin 上与 VLM 叠加后无法在 600 ms 内完成，在 Thor 上也会吃掉大半预算。换用更小的 SAM2 骨干(Hiera-S / T)或降分辨率可提速，但精度需重新评测。**(10-15 已测 Hiera-S,见 §4b「DAM4SAM 骨干 Hiera-L → Hiera-S」:身份耗时约减半，承诺正确 0.720 → 0.671,−0.049 不显著，仍显著高于 Ours。)**
4. **对论文的含义**:DAM4SAM 的精度优势(+0.17)以约 180 倍的身份模块开销为代价(274 ms 对 1.5 ms)。在端侧部署的约束下，这是一个合理的「精度–算力」权衡论点(§5.2 C 的 Pareto 图);但要成立，需要:(a) 独占 GPU 下的 E1 计时(DAM4SAM 的 274 ms 含 RPC 与同机竞争);(b) 至少在一台 Orin / Thor 上实测(E3);(c) 延迟注入评测(E2)证明在真实延迟下 DAM4SAM 的优势缩小或消失。在此之前只能作为讨论，不能作为结论。
