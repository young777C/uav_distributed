# 1019 指标 / 协议讨论(第 0 步判定 stop 之后，讨论稿，待用户拍板)

2026-10-19。起因:1016 §3 第 0 步预注册判定 D = U1 − 永不切换 = +0.089 [+0.009, +0.177] < 0.10 → 停止在现协议上迭代身份模块，转入本讨论。本文只提方案，**未改代码、未跑实验**。

## 0. 纪律(先定，再谈具体改动)

改指标 / 协议发生在看过 dev-B 结果之后，最大风险是「挑一个让我们赢的口径」。约束如下:

1. **理由只谈构念效度**:每项改动都要说明它为什么更接近「无人机实际在做的事」(1006 原则 6),理由不能依赖哪个方法赢。
2. **选指标 / 协议只看 U1 和永不切换**:两者都不是我们的方法;不看 Ours、re-ID 等方法在新口径下的排名。
3. **定稿 → 过 codex → 再跑方法对比**:改动写成新的协议版本或新的 scorer 字段;test(950xx)从未使用，仍然只跑一次。主指标在 test 之前修订是允许的，但要写明日期和理由(修订 1006 §4 的预注册)。
4. **旧口径照常报告**:承诺正确、TR90 都保留在论文表格里。
5. **已有负结果必须如实报告**:Ours 在旧口径上显著不如永不切换(−0.140 [−0.234, −0.049],p = 0.005)。改指标不是为了挽救这个结果。

## 1. 第 0 步说明了什么(`runs/headroom/headroom.{log,json}`,dev-B,n = 40)

身份上限小，不是因为身份不重要，而是现行口径和场景让身份能起作用的帧很少:

| 结构性原因 | 证据 | 属于 |
|---|---|---|
| **遮挡帧计入分母，但没有身份决策可做** | 遮挡 tick 占画面内 tick 的 35–38%;此时目标无框，得分只看承诺 ID「最后匹配的车」:U1 认对 0.46、永不切换 0.45,几乎相同 | 指标 |
| **没有框时沿用旧 ID 记为正确(滞留得分)** | 承诺 ID 本帧无框，但最后匹配的是目标 → 记正确。此时 WHERE 没有框可飞(由 EAR 航点驱动),无人机并没有在跟目标。「停在原地」几乎没有代价，这正是永不切换得分高的原因(1016 §1.1) | 指标 |
| **飞行把目标丢出画面，局被截断** | U1 80 局中 74 局在 90 s 前结束，最后 18 s 全部出画;出画占全部帧 42%。主指标分母不含出画帧，但身份事件随之变少，TR90 被封顶在约 0.23 | 协议 / 飞行 |
| **身份关键时刻少** | 目标在画面里时几乎不会被干扰车抢走(每局 0–0.07 次);切换都发生在目标回来或跟踪器 ID 互换时，每局约 2.3 个回来的缺口 | 场景 |
| 承诺滞回 K = 5(3 s) | 完美身份在可见 tick 上仍有 16% 认错，主要是切换延迟 | 方法共享规则(不改) |

## 2. 指标方面的候选(不改仿真，只改记分;可在已有日志上重算)

| 代号 | 定义 | 角色 | 理由 |
|---|---|---|---|
| **M1 严格跟随率** | 目标可见(在候选框中)的帧里，承诺 ID 本帧的框就是目标的比例;不再沿用旧 ID | 主指标候选 | WHERE 只在有框时飞向承诺的框，这一项度量的就是「无人机此刻在跟谁」 |
| **M2 误跟率** | 目标在画面内的帧里，承诺 ID 本帧的框是干扰车的比例(无人机正在飞向错车) | 安全指标候选 | 跟错受罚、撤销承诺不受罚，与 1016 §2.1「怀疑时宁可撤销」的设计原则一致 |
| M3 再捕获 | 目标重新出现后 6 s 内达到严格跟随的比例(`runs/id_iter/recapture.py` 口径),每个种子先聚合再配对 | 次要指标 | 直接对应「丢了能不能找回」,但每局只有 2–3 个事件，功效低 |
| 旧口径 | 承诺正确、TR90 | 照常报告 | 与 1006 预注册衔接 |

- **遮挡帧单独报告**(滞留认对 / 认错 / 无承诺三类),不再并入主指标。
- **已看过的数字(透明起见)**:第 0 步日志的可见 tick 合并统计(非配对)中，严格跟随 U1 0.79、永不切换 0.61。所以 M1 的上限大约 +0.18,这个数**已被看过，不是盲测**。补救:M1 的判定阈值先写定，再算种子配对值。
- **M1 的上限判定沿用第 0 步阈值**:D_M1 = U1 − 永不切换(配对，r0 / r1 均值)。≥ 0.15 → 在 M1 上迭代;0.10–0.15 → 迭代，test 加大;< 0.10 → 指标层面也不够，只剩协议层面的改动。
- 实现:正式口径要在客户端 scorer 里逐帧计算(改 `acot_client/scoring.py`,只新增字段，先过 codex);上限判定可以先用 tick 日志近似计算。

## 3. 协议方面的候选(改仿真，需要新版本 + 新跑)

**P1 飞行上限诊断(建议先做，成本低)**
- 臂:{U1, 永不切换} × 专家控制,dev-B 40 局,r0。专家控制已有开关(`method.control.expert_control`,`carla_uav_tracking/rollout/env.py:302`):用 GT + PID 的专家动作驱动无人机，身份头照常记分。注意它对准的是「目标 + 相似车」车群的中心，不保证目标始终在画面里(见 §6.2 可解读条件)。
- 可以读出两件事:
  1. 截断和 TR90 封顶中，有多少是我们的飞行造成的(对比第 0 步);
  2. **D_expert = U1 − 永不切换(飞行完美时)**:飞行不再是瓶颈时，这批场景本身还有没有身份上限。
- 旧证据(831,旧协议,n = 10,不可直接比较):专家控制下平均跟随 88.8 s,基本不截断。
- 约 1 小时运行 + 半天(方法配置、冒烟、确认 acot 运行时路径)。开跑前建议先修调度器死锁(1016 §3 第 0 步「运行事故」)。

**P2 身份压力场景(成本高，视 P1 和 M1 结果再定)**
- 在场景生成中加入三类情况:
  - 与目标同类、属性相近的干扰车(语言才能区分);
  - 交汇、超车;
  - 长于跟踪器 `max_age`(8 个 S2 tick = 4.8 s)的遮挡，使目标回来时换了新 ID。这时「永不切换」按构造必然失败。
- 这正对应论文定位里的「杀手场景」。
- 成本:数据生成代码(须先过 codex,按配置开关控制)、新的 dev / test 种子集，约 3–5 天。
- 风险是被质疑「场景为自己设计」。对策:场景参数事先写定，所有基线同场景，标准集和压力集都报告。

**不建议的改动**
- P3 放宽截断(`max_lost_s` 18 s → 跑满 900 帧):出画 18 s 后几乎回不来，多出来的大多是空帧;单独做意义不大。
- K = 5 滞回是所有方法共享的规则，不作为协议项修改。

## 4. 建议的顺序(CVPR 摘要约 11-07,剩约 3 周)

1. **今天**:用户确认 §0 纪律和 §2 的定义与阈值 → 写 M1 / M2 的上限脚本(过 codex),在第 0 步已有日志上算 D_M1(配对)。约半天，不需要新跑。
2. **并行**:修调度器死锁(过 codex)→ P1 飞行上限诊断，约 1 天。
3. **按结果分流**:
   - D_M1 ≥ 0.10:修订主指标(1006 §4,test 未用),回到 1016 的 V1–V5,在 M1 上做第 1–4 步;

   - 两者都 < 0.10:这批场景里身份不是瓶颈 → 做 P2 压力场景，或调整论文定位(另行讨论)。

## 6. 预注册(10-19,在计算任何 D_M1 / D_expert 之前写定)

**6.1 D_M1(已有第 0 步日志,`headroom_devB3`,不新跑;脚本 `runs/headroom/headroom_m1.py`,先过 codex 再运行)**
- 单位:S2 tick(0.6 s),读 `ticks.jsonl`;只用 status 为 complete 的局。这是对逐帧口径的近似，逐帧版本以后在客户端 scorer 实现。
- 每个 tick 的承诺状态与 `runs/id_iter/recapture.py` 相同:承诺 key 本 tick 有框且是目标 = 严格跟随;有框且是干扰车 = 误跟;无框 = 滞留(按最后匹配的车再分滞留认对 / 滞留认错);无承诺。
- **M1(每局)**= 目标有框(候选中含目标)的 tick 中，严格跟随的比例。没有这种 tick 的局记为缺失。
- **M2(每局)**= 目标在画面内(该 tick 帧的 frame_state 为 v / o)的 tick 中，误跟的比例(越低越好)。
- **D_M1** = U1 − 永不切换:每个种子先取 r0 / r1 均值，再对两边都有值的种子求均值;配对 bootstrap CI + 符号翻转 p(与第 0 步同一套函数)。
- **判定(按点估计)**:D_M1 ≥ 0.15 → 在 M1 上迭代身份模块;0.10 ≤ D_M1 < 0.15 → 迭代，但 test 改为 n = 160 或 r = 2;D_M1 < 0.10 → 指标层面不够，只剩协议层面的改动(§4 第 3 步)。
- 只报告、不判定:M2 的差(永不切换 − U1)、遮挡 tick 的分类占比，以及用 tick 近似算出的旧口径承诺正确与 scorer 逐帧值的对照(检验近似是否可靠)。

**6.2 P1 飞行上限诊断(新跑 `flight_ceiling_devB3`)**
- 臂:`u1x_r0` = U1 + 专家控制,`stickyx_r0` = 永不切换 + 专家控制;dev-B 40 局,r0;协议 sim_proxy_v2@3。
- 主读数 **D_expert = M1(U1x)− M1(永不切换 x)**,种子配对，同 6.1 的函数。
- 分流(§4 第 3 步):
  - D_M1 ≥ 0.10 → 修订主指标并回到 V1–V5;
  - D_M1 < 0.10 且 D_expert ≥ 0.10 → 身份上限被飞行掩盖;
  - 两者都 < 0.10 → P2 或调整论文定位。
- 同时报告(描述性):
  - 旧口径承诺正确与 TR90 的 D;
  - 截断局数和平均集长，与第 0 步对比;
  - 场景占比(可见 / 遮挡 / 出画);
  - TR90(U1x)− TR90(U1)。最后一项不是同一实验内的配对，只作描述。
- 运行前提:调度器死锁修复过 codex;2 局冒烟通过(专家控制在 acot 运行时生效：无人机由专家驱动，身份头照常记分)。
- **补充(codex R1,10-19,在看任何 P1 / 冒烟结果之前写定)**:
  - 专家控制是数据生成用的现成专家控制器，不保证目标始终在画面里:mvp 场景开了 `decorrelate_position`,目标可见时专家对准「目标 + 相似车」车群的中心(有距离和瞄准偏移),目标丢失后才改为追目标。
  - **可解读条件** = P1 两臂合计截断局 ≤ 20%,且出画帧占比 ≤ 0.15(第 0 步为 74–76/80 局、0.42)。
  - 条件不满足时:D_expert ≥ 0.10 仍可判「身份上限被飞行掩盖」;D_expert < 0.10 判为「不确定」(专家飞行也没能稳定取景),不据此转 P2。
  - 「TR90(U1x)− TR90(U1)」改为两边各自取均值再相减(各自的局集合，不配对、不给 CI / p),并报告两边局数。

## 7. 结果

**7.1 D_M1(10-19,`runs/headroom/headroom_m1.{log,json}`;脚本 codex R1 → R2 → R3 NO MAJOR 后才运行，`runs/headroom/codex_m1/`)**

| | U1 − 永不切换 | 95% CI | p |
|---|---|---|---|
| **M1 严格跟随率** | **+0.137**(0.822 vs 0.685) | [+0.064, +0.215] | 0.001 |
| M2 误跟率(永不切换 − U1) | +0.035(0.153 vs 0.118) | [−0.030, +0.115] | 0.37 |
| 旧口径承诺正确 | +0.089 | [+0.009, +0.175] | 0.047 |
| TR90 | +0.050 | [+0.001, +0.102] | 0.059 |

- **预注册判定:iterate_bigger_test**(0.10 ≤ D_M1 < 0.15)→ 可以在 M1 上迭代身份模块，但 test 改为 n = 160 或 r = 2。
- **§6.2 分流:D_M1 ≥ 0.10 → 主指标修订为 M1(1006 §4,test 未用),回到 1016 的 V1–V5**。P1 不再影响分流，只作飞行上限的描述性诊断。
- tick 近似可靠：用 tick 近似的旧口径与 scorer 逐帧值平均差 −0.001,平均绝对差 0.002–0.004(每臂 80 局)。
- 遮挡 tick 的承诺状态(U1 / 永不切换):滞留认对 0.46 / 0.45,滞留认错 0.37 / 0.42,误跟 0.16 / 0.13。
- 第 0 步旧口径与 TR90 的数值复现一致(只是 bootstrap 随机数标签不同,CI 端点差 0.002)。

**7.2 上下限与各方法的位置(描述性，在 D_M1 判定之后才计算，不参与任何选择;dev-B @3,n = 40,tick 近似)**

| 指标 | 上限 U1 | 下限 永不切换 | re-ID | Ours(r0+r1) |
|---|---|---|---|---|
| M1 严格跟随率 | 0.822 | 0.685 | 0.684 | 0.533 |
| 旧口径承诺正确 | 0.754 | 0.665 | 0.636 | 0.525 |
| TR90 | 0.230 | 0.179 | 0.193 | 0.164 |

- M1 配对差:Ours − 永不切换 −0.153 [−0.229, −0.080](p < 0.001);Ours − re-ID −0.152 [−0.237, −0.065](p = 0.002);re-ID − 永不切换 −0.001 [−0.079, +0.071];Ours − U1 −0.289。
- 上限 U1 用的是模型自己的飞行;专家飞行下的上限待 P1。

**7.3 为什么永不切换的 M1 有 0.685(描述性，第 0 步 sticky 两遍 80 局)**
- **按局平均放大了短局**:M1 先按局算再平均为 0.685;把所有可见 tick 合并计算只有 0.607。可见 tick 少的局(2–13 个,多为早早丢失目标、被截断的局)M1 0.83,可见 tick 多的局只有 0.55(相关 −0.35)。
- **错误会「自我隐藏」**:承诺一旦不在目标上，无人机就跟着错车飞，目标随即离开画面;此后剩余 tick 中目标仍可见的只占 25%(U1 也是 26%),出画 18 s 后整局截断。错的时段大多不进 M1 分母。M1 以「目标可见」为条件，所以必须和固定时域的 TR90 一起看。
- **跟踪器承担了大部分工作**:开局结束时承诺在目标上的局占 84%(U1 95%);共享的匈牙利跟踪器在短遮挡后多半把原 ID 还给目标(第 0 步回来当 tick 即捕获 0.62),而目标可见时几乎不会被抢。
- 永不切换在可见 tick 上的失分(合并):误跟 0.176(跟踪器把绑定的 ID 换给了干扰车)、滞留认错 0.123 与滞留认对 0.094(目标换了新 ID 回来，绑定的 ID 没有框)。身份模块能争取的就是这三块。

**7.4 调度器已知风险(用户 10-19 决定暂不修)**:调度器进程本身崩溃后，残留的策略容器可能事后写出审计文件，被当成新尝试的审计(codex R5 MAJOR 1);彻底修复要给每次尝试分配 ID 并贯穿客户端、策略和审计文件。正常运行(包括卡死清理)时策略容器会被删除，不受影响。

**7.5 P1 飞行上限诊断(10-19 11:22–13:25,`flight_ceiling_devB3`,两臂 40/40 完成，无卡死 / 中止 / 隔离;`runs/flight_ceiling/headroom_m1_p1.log`)**
- **可解读条件满足**:两臂截断 0/80,出画帧占比 0.03(第 0 步 74–76/80、0.42)。

| 专家飞行下 | U1x − 永不切换 x | 95% CI | p |
|---|---|---|---|
| **M1(D_expert)** | **+0.272**(0.925 vs 0.653) | [+0.174, +0.376] | < 0.001 |
| 旧口径承诺正确 | +0.122(0.929 vs 0.806) | [+0.038, +0.218] | 0.010 |
| TR90 | +0.116(0.902 vs 0.786) | [+0.037, +0.207] | 0.011 |
| M2 误跟率(永不切换 x − U1x) | +0.038(0.065 vs 0.027) | [+0.002, +0.085] | 0.066 |

- **飞行是 TR90 的主瓶颈**:身份都完美(U1)时,TR90 从模型自己飞的 0.230 升到专家飞的 0.902(+0.672,跨实验、不配对、描述性)。
- **模型的飞行掩盖了身份上限**:D_M1 从 0.137(模型飞)升到 0.272(专家飞);旧口径 D 0.089 → 0.122;TR90 的 D 0.050 → 0.116。永不切换的 M1 反而从 0.685 降到 0.653,印证 §7.3 的「错误随目标出画而不计入」。
- 分流不变(D_M1 ≥ 0.10 → 主指标改 M1,回 V1–V5);§6.2 的另一条读数「身份上限被飞行掩盖」(D_expert ≥ 0.10)同样成立，作为补充结论。
- 与旧结论的关系:831 / Stage-3 时期「控制不是 SR 杠杆」是旧协议、旧指标下的结论;在现协议下，身份完美时飞行仍在 74/80 局把目标丢出画面，飞行是 TR90 的最大杠杆。
- **重要限定(10-19 核对代码后补)**:P1 的「专家」拿的是**全知真值**。`rollout/env.py:302` 调 `scene.expert_action(tpos, …, True, …)`,第 4 个参数恒为 True:目标被遮挡或出画时，专家照样知道它的真实位置。我们的模型只有在承诺 ID 有框时才拿到目标位置，其余时间靠 EAR 航点预测。因此 0.230 → 0.902 混合了两部分：控制本身的质量，以及「始终知道目标在哪」的信息优势;后者任何基于视觉的控制器都拿不到。「飞行是 TR90 主瓶颈」应理解为「飞行 + 丢失后的目标定位」的合计上限，不是可部署飞行的上限。若要单独度量控制质量，可让专家只在目标真实可见时拿到位置(丢失后按 PID 内置逻辑外推，5 s 后停止),作为 P1b(未做，待用户决定)。
