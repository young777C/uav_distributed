# 1019 论文叙事与基线设计讨论稿(执行 V1–V5 之前;讨论稿，未做任何改动)

2026-10-19。用户提出的问题：
- 现在的基线没有端到端完成任务，只替换了 WHICH(身份)模块;
- 我们优化其他模块会不会持续推高基线，导致始终超不过它?
- 应该如何固定基线，同时兼顾公平性，得到可靠、有说服力的基线?

## 1. 先把问题拆开：现在的比较到底是什么

当前所有「基线」都是**模块替换式比较**(component swap):
- 所有臂共用同一套底座：协议 @3 的真值候选框与遮挡、匈牙利跟踪器、属性开局、WHERE(真值坐标 + CV)、EAR / IAR / DiT 飞行;
- 只换身份头：re-ID、OA-VAT 身份适配、DeepSORT / OC-SORT、永不切换。

这种设计能回答「在同一个系统里，哪个身份模块更好」,回答不了「哪个**系统**更能完成任务」。

**用户担心的问题是否成立：部分成立，但卡住我们的不是它。**

| 担心 | 实际情况 | 证据 |
|---|---|---|
| 优化共享模块会同步抬高基线 | **成立**:CV WHERE、开局、跟踪器这类共享改进对所有臂同时生效，所以**我们在非身份模块上的贡献在表里永远显示不出来** | 匈牙利跟踪器、CV 都是共享改进 |
| 因此身份比较永远赢不了 | **不成立**:共享改进在期望上不改变身份差距，甚至可能放大它;身份差距只取决于身份模块本身 | 专家飞行下身份上限从 +0.137 扩大到 +0.272;CV 让 TR90 +0.035,但 M1 不变(−0.002) |
| 现在输给基线的原因 | **是身份模块本身**:Ours 的 M1 低于 0 参数的永不切换(−0.153,p < 0.001),这与共享模块无关 | 1019 §7.2 |

**一个已经存在的隐患**:CV WHERE 只在 Ours 上验证、只给了 Ours。如果 CV 算作「底座」,那么 re-ID 和永不切换也必须换成 CV 重跑，否则 TR90 的比较就混入了 WHERE 的差别;如果 CV 算作「我们的方法」,那么在模块级比较里它就是混杂因素。**这一点必须先定。**

## 2. 业界通行做法：两层比较，各回答一个问题

| 层 | 回答的问题 | 怎么比 | 基线 |
|---|---|---|---|
| **A. 系统级(端到端)** | 我们的**整套系统**是否更能完成任务 | 各系统用各自的感知、身份和控制，在同一协议、同一批种子上闭环;任务指标为 TR90、M1、SR(τ)、跟随时长 | 已发表的端到端系统;经典模块化流水线 |
| **B. 模块级(受控)** | 收益来自哪个模块(身份、WHERE、开局、飞行) | 冻结底座，只换一个模块 | 永不切换、re-ID、MOT、OA-VAT 身份适配;以及消融 |
| (C. 上下限) | 空间有多大 | 诊断臂，不进主表 | U1(真值身份)、专家飞行 |

- 论文的主张应当落在 A 层;B 层用来归因。只有 B 层的话，审稿人会问「你的系统比别人的系统好吗」,而我们答不出来。
- **A 层天然解决「推高基线」的问题**:外部系统按其发表版本冻结，我们对任何模块的改进都只算在自己的系统上。

## 3. 如何固定基线

**3.1 A 层：外部系统一次性冻结**
- 每个外部系统固定代码 commit、权重和超参;适配(接口、坐标系、动作空间)写成 diff 并披露(沿用 1004 §5.5 的公平性审计格式)。
- **调参预算相等**:在 dev 上用预注册网格，网格大小与我们的开发历史一起披露(1006 F-d)。
- 冻结时间点在跑 test 之前，写进预注册;之后我们怎么改自己的系统，外部基线都不动。

**3.2 B 层：底座版本化**
- 定义「底座 S1」= 协议 @3 + 匈牙利跟踪器 + 属性开局 + WHERE(EAR 或 CV,需定)+ Stage-2 权重，打标签冻结。
- V1–V5 只改身份头，全部在 S1 上比较。
- 任何共享模块的改进 = 升级到 S2,**所有模块级臂在 S2 上重跑**;不同版本的结果不混比。
- 属于「我们系统独有」的改进(例如以后改进 DiT 飞行)不进 B 层底座，只在 A 层体现。

**3.3 CV 应归在哪里(需要拍板)**
- **建议放进底座**:CV 是通用的工程改进，不是我们的方法贡献;放进底座后，基线也一并获益，审稿人挑不出毛病。
- 代价:re-ID、永不切换要在 CV 底座上重跑(每臂 r0 + r1 共 80 局，约 1.5 小时)。

## 4. 公平性的关键障碍：感知特权

- 我们的系统现在依赖协议给的**真值伪框、按框的真值深度、真值世界坐标**(sim_proxy_v2 的特权感知)。
- 端到端 VLA 跟踪器(OmTrackVLA、ReferTrack、CosFly-VLA 一类)直接从像素输出动作，用不上这些特权。和它们做 A 层比较时，如果我们仍用真值框，就是**我们单方面占便宜**,审稿人一定会指出。
- 两条路:
  1. **我们换成可部署感知**:检测器(可用 CARLA 数据训练，仓库已有 `yolo_train_env`)+ 由框估深度或单目深度，替代真值坐标(1009 §5 早已列为「完整系统对比前必须做」)。工作量最大，但结论最硬。
  2. **A 层只和能接收同样感知的系统比**:例如「检测框 + MOT + 控制器」的模块化流水线，以及 OA-VAT 的完整系统(把它的检测输入换成同一套伪框)。端到端 VLA 只作为参照，并注明感知不对等。

## 5. 叙事选项(与 `acot-uav-paper-writing-kickoff` 的定性对照)

写作 brief 的原定性是：新任务 + 新 benchmark + 系统 + 实证研究,**不是刷榜**。10-19 的结果对原故事线有两处冲击:
- 原第 3 步「墙是 WHICH 不是 WHERE」:现协议下，身份完美时 74/80 局仍因飞行丢目标而截断，飞行同样是墙;
- 我们的身份模块低于 0 参数的零假设。

| 选项 | 主张 | 需要的证据 | 风险 / 工作量 |
|---|---|---|---|
| **N1 系统论文** | ACoT-UAV 端到端完成任务优于外部系统 | A 层:可部署感知 + 2–3 个冻结的外部系统;B 层归因 | 工作量最大(可部署感知、外部系统接入);我们的身份模块现在是短板 |
| **N2 身份模块论文** | 在冻结底座上，我们的身份模块优于零假设、re-ID、MOT | B 层:V1–V5 成功;test 3 臂 × 160 局 | 取决于 V1–V5 能否追平并超过永不切换(目前差 0.15) |
| **N3 任务 + benchmark + 分析论文** | 提出任务和协议，系统地分解难点(身份上限 vs 飞行上限、零假设、指标陷阱),并给出强基线 | 已有的大部分结果;补外部系统作为 benchmark 基线 | 最稳妥，符合原定性;对「方法贡献」的期待较弱，顶会接收取决于 benchmark 的分量 |

**我的建议**:以 **N3 为主线、N2 为方法部分**,A 层先做低成本的两个外部系统。
- **N3 是主线**:benchmark + 上下限分解 + 零假设 + 指标方法学，这些结论今天就站得住，而且是别人没做过的。
- **N2 作为方法部分**:V1–V5 若追平或超过永不切换，就是加分项;若做不到，如实报告负结果，主线不受影响。
- **A 层先做低成本的两个**:
  1. 经典模块化流水线(检测框 + OC-SORT + PID 控制器)——在我们的底座上几乎是现成的;
  2. OA-VAT 完整系统(之前评估过，需要替换的模块最少)。
- 端到端 VLA(OmTrackVLA / ReferTrack)视时间而定，作为参照并注明感知不对等。
- 可部署感知若来不及，在局限性部分明说，并给出「同感知下」的比较。

## 6. 需要拍板

1. 论文主线选 N1 / N2 / N3(建议 N3 + N2)。
2. CV WHERE 是放进底座(所有臂共享，基线重跑)还是算作我们的方法(建议放进底座)。
3. 冻结底座 S1 的内容和时间点(建议现在冻结:@3 + 匈牙利 + 属性开局 + CV + stage2_v5)。
4. A 层外部系统的范围：先做「模块化流水线 + OA-VAT 完整系统」;端到端 VLA 是否纳入。
5. 可部署感知(检测器 + 深度)是否在 CVPR 前做;不做的话，论文要把「感知特权」列为局限。
6. 写作 brief 第 3 步(「墙是 WHICH 不是 WHERE」)按 10-19 的结果改写为「身份和飞行都是墙，并给出两者的上限分解」。
